# 效能量測與第一階段快取

這一輪建立可比較的量測基礎，保留既有移動、碰撞、戰鬥與存檔行為，不新增畫質預設。

## 開啟與關閉

- 平常不顯示面板、不建立樣本陣列、不讀取效能量測時鐘，也不接管 `renderer.info`。
- 在網址加上 `?perf`，例如本機 `http://localhost:5173/?perf`。既有參數後加 `&perf`。這也會開啟既有 `__game` 除錯工具。
- 面板每秒最多更新一次，保存最近 600 個有效幀。可在主控台讀 `__game.perf.snapshot()`，用 `__game.perf.reset()` 開始一段新的路線。
- `__game.perf.enabled = false` 停止收樣、釋放樣本陣列並隱藏面板；設回 `true` 會重新收樣。拿掉網址的 `perf` 並重新載入也會關閉。
- `?debug` 或開發模式本身不會開啟效能量測。

## 讀值的意思

- `p50Ms`、`p95Ms`、`meanMs`：最近至多 600 幀的真實幀間隔，單位毫秒。真實 200 ms 停頓就是 200 ms，不會被遊戲步進的 50 ms 上限截短。
- `longFrames`：自上次重設以來大於 50 ms 的幀數；`windowLongFrames` 是目前視窗內的數量。`sampleCount` 是總有效幀數。
- `updateCpuMs`、`renderCpuMs`：最近一幀的主執行緒更新／渲染提交耗時，**不是 GPU 計時**，也不是實機 FPS 保證。
- `renderCalls`、`triangles`、`lines`、`points`：最近完整一個遊戲幀。Three r149 預設每次 `render()` 自動清除資料；診斷模式在整幀渲染前暫時關閉 `autoReset` 並清除一次，收完後還原，故包含陰影、場景及所有 Bloom／合成 pass。
- `geometries`、`textures`、`programs`：Three renderer 的資源計數，不是總記憶體用量。
- `pixelRatio`、`postProcessing`、`bloom`、`viewport`、`room`：讀值當下的畫質與場景條件。
- 啟動、背景頁籤、恢復可見的第一幀不採樣；切換頁籤時會重設量測視窗與畫質未完成的觀察窗，避免把背景停頓誤判為卡頓。

遊戲步進仍是 `Math.min(rawDt, 0.05)`，沒有補跑物理或改角色速度。自動畫質沿用既有門檻、解析度下調與 Bloom 規則，只改成讀取未截斷的有效間隔。因此嚴重掉幀時，可能比舊版更早正確降畫質。

## 如何公平比較

1. 固定同一部裝置、瀏覽器、視窗尺寸、方向、電源模式與路線；避免切到背景或同時執行大量工作。
2. 先暖機，等字型、首次房間建立等工作完成。首次進房間停頓則另外記錄，不能和已快取的第二次混比。
3. 確認兩次記錄的 DPR、Bloom、後製狀態相同，再重設量測並走相同路線。既有自動畫質仍開著，若中途畫質改變，需分段重測，不能把降解析度的效果當成本次快取收益。
4. 建議路線：校門、四維道、照片街區、游泳館內外、雨天。分別記錄 p50／p95、長幀、完整 render calls 與資源計數。
5. 每段都用同樣的診斷開關。診斷本身有少量成本；600 格樣本與每秒一次排序有界，關閉時不做這些工作。

## 快取失效與維護

- 小地圖的玩家裁切、視角扇形與角色箭頭仍約每 80 ms 更新。室內仍顯示房間名稱，不畫戶外底圖。
- 小地圖靜態底圖只保存一張額外的 1040×800 canvas，像素約 3.2 MiB；不隨房間或尺寸累積多份快取。
- 建築圖示登記、圖示順序／標準欄位變更、尺寸、字型完成／變更會重畫底圖。自訂 `draw` 若讀取外部可變資料，更新資料後呼叫 `invalidateMapShapes()`。
- 有無秘寶地圖、故事收集狀態與標記位置改變，只重組標記圖層，不重畫 900 個紙張雜點。完整地圖開啟時仍走完整繪圖，保留玩家標記與原本覆蓋順序。
- `__game.miniMapCacheStats()` 可讀底圖／合成次數、已套用／待套用字型版本與各種失效原因計數。同一次重畫可以有多個原因。這是工作量計數，不是 FPS。測試中 200 次未變更更新只有一次底圖和一次合成。
- 區域快取保留公開 `world.zones` 陣列行為：新增、移除、重排、優先序變更會重新排序；未變更查詢不複製或排序；相同優先序維持登記順序。
- 互動文字與顯示狀態相同時不再重寫 DOM，目標位置與鏡頭投影仍逐幀更新。

## 檢查

執行 `npm test`、`npm run check`、`npm run build`，再執行 `npm run smoke`。CI 也會依序執行。

Node 測試涵蓋原始／步進時間、背景恢復、畫質觀察窗、診斷開關、完整多 pass 統計、快取失效、舊地圖繪圖指令／樣式／順序對照、區域優先序、重複 DOM 寫入及起始畫面版本。Playwright 檢查真實遊戲啟動、室內進出、手機搖桿，以及診斷和小地圖整合。

無頭瀏覽器使用軟體渲染，不能當手機或桌機效能基準。本次未量測任何實機 FPS；需要上述同條件實測，才能量化改善幅度。


### 字型與冒煙測試

網路字型依顯示的字元載入子集。第一次開地圖或走到入口，可能在原本的 `document.fonts.ready` 已完成後再載入新字型，這時底圖重畫是必要的。冒煙測試先顯示這些狀態並等版面、字型及小地圖更新完成，再以精確次數檢查持有狀態與移動；另外刻意送出晚到的 `loadingdone`／`loadingerror` 事件，確認每次只重畫一次且之後恢復快取。CI 記錄預熱與正式斷言前後的原因計數，不放寬為容許任意次數重畫。


## iPhone 13 Pro／60幀開發基準（2026-10-24使用者要求）

所有後續開發沿用此目標：正常遊玩時以60幀為基準，即每幀1000÷60≈16.67ms。此為產品要求，不是目前已達成的證明。先做靜態不透明幾何按相容材質／空間區塊合批，重複形狀沿用實例；保留可裁切範圍、玻璃排序、相機射線與真碰撞，不把全棟合成單一巨型繪製批次。

開發階段的提交次數／三角形檢查是防止負擔反彈的預警，不能單獨保證幀率。軟體CI的低幀率亦不能直接推算手機GPU幀率。須附同畫質、同位置的前後完整幀統計，自動畫質的DPR／Bloom變化另列。

實機發布驗收使用 iPhone 13 Pro、實際Safari及原正式網址；記錄iOS／Safari版本、直橫方向、畫面像素比與遊戲實際DPR、後製／陰影、電源模式及是否熱機。前景可見且字型／首次建模載入完成後，持續至少10分鐘走完達賢戶外／入館／中庭上下樓／電梯／返回戶外，覆蓋午後與夜景，另記首次進館停頓。60幀螢幕取樣p50應約16.67ms，p95目標不高於16.67ms（含量測誤差須揭露原始值），不能只報平均FPS而掩蓋長幀；任何明顯卡頓須定位並修正。若裝置以120Hz回報，保留原始幀間隔，不把120Hz/60Hz混成一組比較。

目前尚無本輪iPhone13Pro實機證據。取得實機證據前，不標記此目標通過，也不把降低解析度後的桌機模擬結果視為等效。


### 達賢室內固定構件合批（2026-10-24，候選版本）

參考組員的山居合批 `9f85863`、`docs/bake.md` 與 `docs/prefabs.md`。只處理延後建立的達賢室內，不搬尚未完成的整區重建。沿用原材質與 shader，16單位空間格／4單位高度帶；原物件保留名稱、階層、碰撞及相機射線，另建繪製副本。玻璃、動態與燈具維持獨立，陰影設定不減少。其他區域／任意自訂物件需另驗，不能直接套用這個限定用途工具。
